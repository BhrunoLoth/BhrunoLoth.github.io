Reliable browser automation and job orchestration

A generic engineering case study demonstrating job lifecycle design, resilient retries, outcome classification and observable workflows.

TypeScriptPlaywrightJob statesRetriesSQLTestingObservability

Engineering challenge

Browser automation needs more than scripts that click buttons. Reliable systems must classify outcomes, recover safely from transient failures, keep work observable and escalate uncertain cases for review.

Explicit job states

Represent work as queued, running, completed, retryable or requiring manual review. Distinguish an unverified result from a confirmed failure.

Bounded recovery

Use timeouts, retries and backoff only where repeat execution is safe. Non-idempotent operations require stronger confirmation before rerunning.

Observability

Emit structured events, link job outcomes to a run identifier and make system health inspectable without exposing account data.

Original illustrative TypeScript

Clean-room example built solely to illustrate failure classification. It is not client code.

type Result =
  | { kind: "success"; reference: string }
  | { kind: "temporary_failure" }
  | { kind: "unknown_state" };

type Decision = "complete" | "retry" | "manual_review";

function decide(result: Result, attempts: number): Decision {
  if (result.kind === "success") return "complete";
  if (result.kind === "unknown_state") return "manual_review";
  return attempts < 3 ? "retry" : "manual_review";
}

// Example: an unknown outcome must not be auto-repeated.
console.assert(decide({ kind: "unknown_state" }, 1)
  === "manual_review");
